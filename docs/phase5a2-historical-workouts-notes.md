# Phase 5A.2 — Historical Workouts, Authoritative Duration, Manual Calories, Provenance

Second subphase of the approved Phase 5A split. Adds migration 014 (the retired 4C reservation is superseded; 014 now belongs to this phase by explicit approval).

## The real-world problem

The workout model assumed live capture: `start_time` = when New workout was pressed, `end_time` = when Complete was pressed. A ~60-minute workout performed away from the app and typed in over ~7 minutes therefore persisted as a **7-minute workout** — data-entry time masquerading as activity time. The system must distinguish live capture, manual/historical capture, and (future) imported data.

## Provenance model (migration 014)

`source TEXT NOT NULL DEFAULT 'legacy'` with CHECK `('legacy','live','manual','imported')`, plus `calories_burned INTEGER NULL CHECK (>= 0)`. **Legacy classification rationale:** existing rows cannot truthfully be labeled `live` — some were entered after the fact through the old live workflow — so the default classifies every pre-014 row as explicitly *unknown/legacy* rather than falsely labeled. Both live creation paths (`POST /api/workouts` live branch and routine start) now write `source: 'live'` explicitly, never relying on the default; historical creation writes `source: 'manual'`. `imported` is reserved only — no import behavior exists. `legacy` is a data-integrity state and is never surfaced to users.

## Calories: informational only

`calories_burned` is user-entered, whole calories, **NULL = not recorded, 0 = explicitly zero** — never conflated. No estimation from exercises/duration/weight/HR/MET; no nutrition-target interaction. **Double-counting warning:** the target model's maintenance already embeds habitual activity via the bodyweight multiplier (×10/12/14), so subtracting or "eating back" exercise calories would double-count. Any future exercise-aware target feature must be explicitly scoped; recording calories today does not mean "eat these back." Displayed factually on the completed detail as `Calories burned N`, only when non-null.

## Historical-entry lifecycle (the approved architecture)

A historical workout is created directly in the **existing correction state**: `status = 'in_progress'` **with** `completed_duration_seconds` frozen from birth, `source = 'manual'`, actual `workout_date`/`start_time`/`end_time`. The active-session invariant (`in_progress AND completed_duration_seconds IS NULL` — partial unique index 008 + `findActiveTrainingSession`) is untouched and ignores the draft by construction, so it: never triggers the conflict modal, coexists with one live active workout, and stays fully editable for exercise/set entry (the read-only rule keys on `completed`). The existing **Complete workout** action finalizes it. **Narrow forced change in the complete route:** `end_time: existing.end_time ?? nowIso` — a historical row's authoritative end instant survives finalization, while live first-completions and post-reopen recompletions (where `end_time` is null at that moment) behave byte-identically to before. The 2J COALESCE keeps the frozen duration authoritative in every path — data-entry elapsed time can never replace it.

## User-facing state: `Editing workout`

The database status stays `in_progress` (no new status value). The user-facing label for `source='manual'` + `in_progress` + frozen duration is **`Editing workout`** via the shared `workoutStatusLabel` helper in `lib/workout.ts`, used by both SessionHeader and SessionCard (single source of the condition). This label is deliberately universal because the same tuple also matches a *reopened* manual workout — the repository cannot distinguish the two without a new schema field, and `Editing workout` is truthful for both (this is the documented limitation and the approved wording). Live active workouts keep `In progress`; legacy/live reopened rows keep their existing labels and are never falsely labeled manual; `Imported` is never rendered. Status pill colors are unchanged (no new badge taxonomy).

## Creation flow and manual metadata correction

Train hub → secondary **Log past workout** (primary New workout untouched) → Title + Date + Start + **Duration in minutes** (approved input model; end instant derived) + optional calories/notes → draft created → routed to `/workouts/[id]` showing the true duration immediately → exercises/sets entered → Complete workout. At any point, **Edit workout details** on the detail header (manual-source rows only) corrects Date/Start/Duration/Calories through an explicit `mode: 'manual_metadata'` PATCH: the server verifies ownership and `source='manual'` (legacy/live rows are rejected), validates through the same pure helper, and derives `workout_date`/`start_time`/`end_time`/`completed_duration_seconds` itself — the client can never set status, source, or duration fields directly, and the existing title/notes PATCH (including its completed-row lock) is preserved byte-for-byte. The correction deliberately replaces the frozen duration and re-derives `end_time` — an explicit correction is distinct from live recompletion, where the frozen value remains protected. Status is never touched: a completed row stays completed (metadata correction does not reopen exercise editing — the existing Reopen workflow remains that mechanism), a draft stays a draft.

## Validation and local time

`validateManualWorkoutMetadata` (pure, runtime-tested): valid `YYYY-MM-DD` + `HH:mm` combined in ONE local `new Date()` parse (no Z-append, no offset arithmetic — the harness proves 8 PM stays hour 20 and a 11:30 PM workout keeps its entered calendar date while its end crosses midnight); start not materially future (2-minute clock-skew tolerance); duration an integer > 0 and ≤ 1440 (24h — a workout-model bound only, NOT inherited by 5A.3 activity sessions); calories optional integer ≥ 0, empty clears to NULL. `workout_date` persists the entered local calendar date verbatim.

## Physical-QA correction (pre-checkpoint): Safari native time control clipping

Physical QA in Safari rejected a valid ~1:00 PM start (current local time ~2:46 PM) and showed the Start time and Calories fields clipped past the card's right edge. **Root cause: layout, not validation.** Safari's segmented native time control (hh:mm + AM/PM) has a much larger intrinsic minimum width than Chromium's, and CSS grid items default to `min-width: auto` — so in the 2-column rows the control blew out its 1fr column and clipped, leaving the AM/PM segment unreachable. An incomplete time control reports an empty value, so both the native `required` constraint and the shared validator correctly rejected what looked like a valid entry. The shared validator was proven correct at runtime against the exact reported scenario (now = 2:46 PM: 1:00/1:30/2:40/2:45 PM and 1:00 AM accepted; +1 min accepted within the 2-minute skew tolerance; +3 min and a still-future 11:30 PM rejected; yesterday 11:30 PM accepted with the midnight-crossing duration keeping the entered calendar date) — no validation rules were loosened or changed.

**Fix (2 feature files):** `LogPastWorkoutForm` and `SessionHeader`'s edit-details form (same structure, same inputs — the identical defect class, fixed together) reflow as `grid grid-cols-1 sm:grid-cols-2` with `min-w-0` on every field cell and input: single-column stack on mobile (the time control gets the full card width — measured 311px at 375px viewport vs the clipped 152px column before), two comfortable ~348px columns from `sm:` up, no 4-column layout, no horizontal overflow, no JS viewport measurement, shell invariants untouched. Native attribute audit: the time inputs carry only `required` (kept — consistent with the shared validator); duration `min/max/step` and calories `min/step` agree exactly with the shared validation, so nothing was removed. One 5A.2-harness pin retargeted (it had pinned the pre-correction 2-column pairs); new layout and physical-QA time-semantics sections added. No migration change.

## Physical-QA correction 2 (pre-checkpoint): explicit segmented time entry

After the layout fix, Safari QA exposed a second usability defect in the same field: the native segmented `<input type="time">` can **look fully populated (e.g. "01:00 PM") while Safari still treats a segment as uncommitted**, reporting an empty value — the field appears filled but submission behaves as if it isn't. This is a native-control usability issue, not a validation flaw. **Fix (same 2 form files + conversion helpers in the already-in-scope `lib/workout.ts`):** both manual forms replace the native time input with an explicit ForgeFitOS segmented control — three native selects (the existing FastingControls/onboarding convention) for **Hour (1–12), Minute (00–59), AM/PM** under a visible "Start time" group label (`role="group"`, per-select aria-labels). Hour and AM/PM start as placeholders and Minute defaults visibly to `00`, so the control can never look complete unless it is; an incomplete state is guarded before shared validation with "Enter a complete start time." and can never serialize. Pure helpers `composeTime12To24` / `splitTime24To12` build and prefill the unchanged local 24-hour `HH:mm` contract (runtime-tested: 1 AM→01:00, 1 PM→13:00, 12 AM→00:00, 12 PM→12:00, 11:30 PM→23:30; prefills 00:30→12:30 AM, 12:30→12:30 PM, 13:05→1:05 PM, 23:59→11:59 PM; full 24-hour round-trip) — no Z-append, no offset arithmetic, no server-contract change, no validation loosening. Verified live: fresh segments read placeholder/00/placeholder, the stored 13:05 prefilled as 1/05/PM, the incomplete guard fired with the exact copy, a completed 1/00/PM passed composition + shared validation through to the API, and all three selects fit a 375px card (101px each) with zero overflow. Two 5A.2-harness pins from correction 1 were retargeted (they pinned the now-removed native input); runtime sections 22–23 added.

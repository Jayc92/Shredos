# Phase 5A.3 — Intentional Activity Sessions Notes

Third subphase of the approved Phase 5A split (migration 015). Adds first-class intentional activity sessions — walking first, with the full restrained type selector — while leaving passive daily steps and strength training exactly where they were.

## Three-table boundary (strict)

`workout_sessions` = structured strength training (exercises/sets, PR/volume, live+historical lifecycle). `activity_sessions` = intentional non-strength activity/cardio sessions — simple completed records, many per day, no lifecycle, no reopen. `daily_activity_logs` = passive per-day aggregate steps, one row per user/day, unchanged. **No cross-writing, ever:** sessions never write steps or daily aggregates, daily totals are never derived from sessions, and session calories never touch nutrition targets (informational only — the target model's activity multiplier already embeds habitual movement; eat-back would double-count). An intentional walk obviously contributes to real-world steps; reconciling that is explicitly a future import-layer concern, kept solvable because the concepts never share rows and sessions carry provenance.

## Schema rationale (migration 015)

Smallest durable schema: nine-value `activity_type` TEXT CHECK (`walk/run/cycle/hike/row/elliptical/stair_climber/swim/other` — extensions are rare additive migrations; `other` absorbs the tail); authoritative local `activity_date`; **optional `started_at`** ("I walked 42 minutes yesterday" is a valid record with no known instant); required `duration_seconds > 0`; canonical `distance_meters NUMERIC(10,2) > 0` (the 011/SetRow convention — no value+unit pair, no unit-preference system); `calories_burned` with the 014 NULL-vs-0 rule; **`source` with NO DEFAULT and no `legacy`** (a new table has no unknowable rows; every writer must state provenance — the 5A.2 lesson formalized; `live`/`imported` are reserved vocabulary with no timer or integrations yet; future providers compose with `source='imported'` via an additive `provider` column later rather than polluting the taxonomy). **Deliberately omitted:** `ended_at` (derived when a start exists; a second persisted timestamp is a consistency liability through edits), `title`, `intensity`/`pace`/`elevation`, `metadata JSONB`, `steps`, uniqueness constraints (two walks a day are legitimate). Per-operation own-row RLS, the standard `updated_at` trigger, one `(user_id, activity_date DESC)` index, PostgREST reload notify.

## Server-side writes (approved architectural change)

The original audit proposed the fasting direct-write pattern; the approval overrode it: activity sessions have enough semantic rules that the write boundary is **server-authoritative**. `POST /api/activity-sessions` creates (auth → shared pure validation → server-derived insert with `source: 'manual'` supplied only by the server — the payload cannot influence source/id/user_id); `PATCH/DELETE /api/activity-sessions/[id]` correct and remove **manual rows only** (ownership then `source === 'manual'` enforced; `live`/`imported` rows are rejected until a future phase gives them explicit correction semantics), with the PATCH payload restricted to the seven editable fields (unknown keys rejected explicitly, 2M convention) and the update object structurally unable to carry id/user_id/source/created_at. No bulk endpoints. The existing `/api/activity` route continues to mean passive daily steps and is byte-unchanged.

## Local date, optional start time, and the toggle UX

`activity_date` is the authoritative local calendar date. With a start time: the segmented Hour/Minute/AM-PM control (the 5A.2 standard — native `type="time"` never returns) composes a local `HH:mm`, parsed once with the date, 2-minute clock-skew tolerance, midnight-crossing durations keep the entered date. Without one: `started_at = NULL` and the future rule is simply `activity_date ≤ today` — the client checks against the user's real local today, and the server backstops with a one-day skew allowance past its own UTC date (it cannot know the user's timezone; the client remains the strict check). **Optional-time UX:** per the approval's suggestion, an explicit **"Add start time" checkbox** replaces ambiguous placeholders — unchecked means "no start time" with zero false-complete risk, checked reveals the segmented group which must then be complete ("Enter a complete start time."); unchecking during an edit deliberately clears `started_at` back to NULL.

## Distance

Canonical meters stored; miles entered/displayed (US-first, matching SetRow). The client sends the raw miles value; the **server** converts once via the shared `milesToMeters` (×1609.34, 2dp). Prefill converts back with `metersToMiles` at the same 2dp on both directions, which the harness proves round-trip stable across representative values — no cumulative edit drift.

## CRUD, list, and page placement

Create/edit/delete all ship now (the fasting/workout lesson: never ship immutable mistakes). `/activity` keeps its entire passive flow untouched (DateNav, steps form, goal, Last 7 days) and gains one additive section below it — **Intentional activity** — with the Add activity expandable card (type selector defaulting Walk, Date, optional segmented start, Duration, Distance mi, Calories, Notes) and Recent activities (10 most recent: label · duration · distance · calories when recorded — explicit 0 renders as 0, NULL renders nothing · date · start time when known · truncated notes; labeled Pencil/Trash on manual rows with the established confirm pattern; inline edit form). No new route, no modal, no navigation change; Activity stays under Progress.

`composeTime12To24`/`splitTime24To12` moved verbatim from `lib/workout.ts` to the neutral **`src/lib/local-time.ts`**; workout AND activity forms import from there. Behavior is byte-equivalent — the 5A.2 harness's runtime conversion suite (all 12/24h cases, prefills, full round-trip) still executes against the relocated functions and stays green, with its import retargeted (flagged). One additional flagged retarget: 5A.2's migration-boundary pin ("exactly 14, no 015") → "5A.2 added only 014; schema through 014 intact," since 015 is this approved phase.

## Deferred (unchanged from the approved design)

Live activity timer (Start/Stop walk — manual logging solves the immediate need; `source='live'` is reserved so the future feature is additive); all integrations/imports (Apple Health/Watch, Garmin, Fitbit, Strava, Runna, SmartGym, CSV/JSON) and import-layer dedup/provider columns; Coach, weekly-review, Progress-overview, and nutrition consumers (store correct data first — `/activity` is the only reader); activity-session steps.

## Physical-QA correction (pre-checkpoint): the weekly step average

Authenticated QA reported that saving yesterday's steps didn't visibly move the "Last 7 days" average. Investigation ruled out every data-path suspect with evidence: the window was already a correct inclusive **today + previous 6 local calendar days** (`gte/lte` on local DATE strings, no UTC shifting anywhere — `todayISO` is date-fns local), the upsert was correct, and staleness was **empirically disproven** on this exact Next version (an auth-free replica of the page's save-then-`router.refresh()`-then-Link-navigate pattern served fresh aggregates). The real cause was **semantics**: the average deliberately divided by *logged days only* (documented since Phase 1F/1G and mirrored in weekly-review), so a new entry close to the existing logged-days average barely moved the number — and the bare "avg steps" label never said which average it was. Logged-days averaging also inflates the result when logging is incomplete.

**The authoritative rule (approved Option C):** `7-day step average = SUM(daily_activity_logs.steps across today + previous 6 local calendar days) ÷ 7`, missing/unlogged days counting as **zero**. One shared helper (`averageDailySteps` + `STEP_WEEK_DAYS` in weekly-review) now backs every live consumer: the /activity "Last 7 days" tile (relabeled **"7-day avg"**), weekly-review's flat `avgStepsLogged` fact, and `computeWeeklyActivity.averageSteps` (check-in's Activity card, relabeled **"average daily steps this week"**). The **"X/7 days logged"** figures everywhere remain the untouched completeness/confidence signal — incomplete logging stays visible, it just no longer inflates the average. Coach/weekly-review thresholds were not changed (the step nudge keys on logged-day counts, which kept their semantics); `progress-summary`'s logged-days math sits entirely on the documented dead `fetchProgressSummary` path (zero live callers) and stays byte-untouched per the standing rule — pinned. Intentional `activity_sessions` remain fully excluded from every step aggregate (no distance→steps or calories→steps conversion exists), pinned at runtime.

**Correction scope: 3 feature files** (activity/page.tsx, weekly-review.ts, check-in/page.tsx). **Approved semantics retargets (documented behavior change, not regression relaxation):** 3A's reducer fixture (30,000 over 3 logged days: 10,000 → **4,286**), 3C's review fixture ×2 (20,000 over 2 days: 10,000 → **2,857**), and 4B.5's expression + label pins. The 5A.3 harness gained a runtime section proving the user-approved fixture (56,000/7 = 8,000; correcting a 6,000 day to 12,000 → 62,000/7 → 8,857 with the existing Math.round convention), inclusive-boundary/exclusion behavior, single-helper consistency, and honest empty states (no fake zero average).

## Physical-QA corrections 2 and 3 (pre-checkpoint): date isolation + table grants

**Daily steps bled across dates.** Authenticated QA saw one date's step value follow the user through DateNav and, worse, get saved onto other dates. Root cause **empirically reproduced** (auth-free replica, keyed-vs-unkeyed forms side by side): `ActivityLogForm` initializes its fields with `useState(existingLog…)`, and React preserves the same-position component instance across `?date=` navigations — the initializer never re-runs, so the previous date's value remains displayed (the unkeyed replica showed `state="17101"` over `prop="12345"` after navigating), and pressing Save writes that stale value to the newly selected date. The database layer was never wrong: the API upserts on the requested `logged_date` against the `UNIQUE (user_id, logged_date)` contract. **Fix:** `key={date}` on the form — each calendar day gets its own instance, reinitialized from that date's server-fetched row (the keyed replica tracked its prop exactly). No forced reloads, no duplicated client aggregate state.

**Activity-session writes failed with "permission denied for table activity_sessions."** That error text is a table **privilege** failure, not an RLS rejection. Root cause: every working user-owned table (002 food, 003 workouts, 004 routines, 005 daily activity) carries the project's explicit `GRANT SELECT, INSERT, UPDATE, DELETE … TO authenticated` — **migration 015 omitted it**, and RLS policies alone grant nothing. **Fix: corrective migration `016_phase5a3_activity_session_grants.sql`** containing only the identical minimal grant plus the PostgREST reload notify — nothing to `anon`, no service-role grant, applied-history 015 untouched (its RLS and four own-row policies remain the row-scoping authority; the routes keep using the cookie-bound authenticated server client, never a service role). Two in-phase harness retargets from these corrections (the migration-count pin and the form-mount pin) are flagged; the weekly-average semantics fixed in correction 1 are unchanged.

## Phase 5A.4 — approved design record (NOT implemented; begins from the 5A.3 checkpoint)

Approved at the post-5A.3 design checkpoint. Migration **017** (additive only): `daily_activity_logs` gains canonical `distance_meters NUMERIC(10,2) NULL CHECK (IS NULL OR >= 0)`, and **steps becomes nullable with its DEFAULT dropped** — required for honest missing-data semantics. Authoritative rule for BOTH fields: **NULL = not recorded, 0 = explicitly recorded zero.** A distance-only day must not fabricate zero steps; steps-only, distance-only, both, and zero-steps-plus-positive-distance are all valid; **no steps/distance conversion or estimation in either direction, ever.** Miles in UI, canonical meters in DB via the existing shared `milesToMeters`/`metersToMiles` (no second conversion constant). Validation (**D5 as modified**): blank → NULL, 0 → valid explicit zero, positive finite numeric → valid, negative/NaN/Infinity/malformed → reject, bounded only by NUMERIC(10,2) storage precision — **no arbitrary product-level maximum distance** (plausibility is a warning concern for a later validation-quality phase, never a brittle hard cap). **Reconciliation warning (D3):** intentional-session distance for the viewed date is a COMPONENT of the daily aggregate — when the session sum exceeds the recorded daily aggregate distance, `/activity` shows an informational warning; it never blocks a save, never mutates either value, never auto-increases the aggregate, never auto-reduces sessions. **Deferred (D4/D6):** 7-day distance averages, distance Progress facts, Coach consumption, Energy Balance consumption, and the session plausibility warning (later phase; may use activity context, duration, distance, derived speed/pace, aggregate/session consistency, imported-source confidence). Scope: max 8 feature/source files. Store correct data first. No new grants needed — the 005 table-level grant covers added columns (the 016 lesson, inverted). Migrations 015/016 stay untouched; 017 is new and additive.

## Core future energy model (architectural requirement)

**Aggregate daily signals** (steps, daily distance, future active energy) versus **session-level components** (workouts, walks, runs, other intentional activities): session components are generally *contained within* the aggregate daily signals. **Never blindly sum them together.** Example future rule: Apple Health daily active energy 850 kcal with workout/session calories of 520 kcal must NOT be reported as 1,370 kcal burned — the session value is evidence/components within the aggregate. This reconciliation becomes part of the future **Energy Balance + Adaptive Coach** phase, which consumes calories consumed, daily movement, intentional activities, workout calories, aggregate active energy, weight trend, estimated TDEE, and expected-vs-actual weight change, applying conservative adaptive 100–200 kcal adjustments weighted by logging confidence/completeness — with **no automatic eat-back** of exercise calories. This is a core ForgeFitOS product requirement, not a side feature.

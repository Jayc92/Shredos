## QA correction (post-delivery, same phase)

Real-user testing surfaced four defects; three are corrected here, one is diagnosed and held for approval.

**1. Profile double scrollbar — diagnosed, then fixed on approval.** Measured with a static reproduction of the real shell + profile DOM using the compiled CSS at 375x812 / 600x900 / 800x900 / 1280x900: the profile route introduces **no** nested scroll owner (`main` is the only scrollable element; document overflow is 0 at exact integer viewports; every Card is `overflow-hidden`, which clips and can never scroll). The second, outermost scrollbar is the **document** itself, which becomes a scroll owner whenever the statically sized shell (`h-screen` = 100vh on the app wrapper) plus `min-h-screen` on `body` exceed the *actual visual viewport* — demonstrably (measured) a 1px excess creates the twin-scrollbar state. Real-world triggers: mobile Safari's URL-bar dynamic viewport, and browser-zoom / OS display-scaling fractional rounding. Two sizing-based attempts (`h-screen` → `h-dvh` → `h-full` percentage chain) failed physical QA. Live instrumentation of the real built app (temporary standalone diagnostic route rendering the exact shell hierarchy with the real Sidebar/TopBar/MobileBottomNav; deleted after measurement) had already disproved the flex-minimum-size hypothesis: the content column carries `min-h-0` (4B.2), `main`'s automatic flex minimum is already zero (flex items with `overflow` ≠ `visible` have a zero automatic minimum size), and at exact integer viewports the document had a zero scroll range. The decisive live physical-Safari experiment then proved the real root cause: **any in-flow shell, however sized, leaves the root document itself a scrollable path** — under fractional viewports (zoom rounding, display scaling, classic always-on scrollbars, URL-bar states) an in-flow viewport-sized box can exceed the root's client box (measured: body client 906 vs html client 905), so the document paints its own scrollbar alongside `main`'s.

**Final fix — the viewport-pinned shell.** The authenticated wrapper in `src/app/(app)/layout.tsx` is now `fixed inset-0 flex overflow-hidden bg-canvas`: pinned to the viewport and **removed from normal document flow**, with no height class at all (`inset-0` binds both edges). With nothing in flow, the document has nothing to scroll — `main` owns app-content scrolling *by construction*, in every engine, at every zoom, in every scrollbar mode, with **no** html/body `overflow` lock, no JS sizing, no resize listeners. The failed height experiments were removed as no longer required: `html { height: 100% }` is gone from `globals.css` (the file is byte-identical to the checkpoint again) and the root body carries **no sizing class** (`font-sans antialiased bg-canvas text-ink`) — restoring a viewport-unit `min-h-screen` box would put the proven failure class back into document flow, and body height is irrelevant now (`bg-canvas` propagates to the viewport canvas; login sizes itself with its own `min-h-screen` wrapper and scrolls as an ordinary document; onboarding lives inside the `(app)` shell and has scrolled via `main` since 4B.2 — unchanged). Verified live in the real built app at 375x812 / 600x900 / 800x900 / 1280x900: document `scrollHeight === clientHeight` everywhere, body rect height 0 on shell routes, `main` the only vertical scroll owner, no horizontal overflow, bottom nav anchored to the viewport bottom with the 72px `main` clearance intact, and the Radix Select portal (z-[200], body-level) opens opaque **above** the pinned shell (the shell sets no z-index). Harness section 25 pins the proven mechanism and **replaces the same-phase h-dvh / percentage-chain assertions (correction replacement of in-phase experiments, not a retarget of retired prior-phase markup)**: shell `fixed inset-0 flex overflow-hidden`, no viewport-height ownership on the shell, height-chain experiment removed from globals, unsized body, no overflow lock, no JS viewport sizing, the `min-h-0`/`overflow-y-auto` flex constraints, byte-anchored main/sidebar/TopBar/bottom-nav/`lg` chrome, login document-flow, and portal-above-shell layering.

**2. Select menu transparency — fixed in the shared primitive.** Root cause is generic, in `src/components/ui/select.tsx`, not onboarding: `SelectContent` used legacy `bg-popover text-popover-foreground border-border`, and under the live `html.dark` those custom properties hold `oklch()` values consumed as `hsl(var(--…))` — invalid at computed-value time, so `background-color` collapsed to transparent and page content bled through the open menu (the same IACVT mechanism documented in 4B.1). The menu chrome now uses semantic tokens (`bg-surface text-ink border-edge shadow-lg`), the item highlight `focus:bg-surface-sunken focus:text-ink` (the legacy `focus:bg-accent` highlight was equally invalid — invisible), the separator `bg-edge-subtle`. Portal-into-body, `z-[200]`, animations, Radix behavior, keyboard handling, and every option/value are untouched; no onboarding file changed. Affected consumers (all fixed by the shared change): onboarding Step 3 Preferred day / Time of day / fasting goal, profile Day / Time / fasting goal, QuickAddPanel, RecentFoodPanel. The trigger's own legacy tokens (`bg-background border-input`) render like the sibling legacy inputs and stay in the 4B.6D token audit.

**3. Add-food required asterisks — labels now match the contract.** The actual contract (client + `/api/food-logs` POST): `food_name` required, `calories` required (`>= 0`), `protein_g/carbs_g/fat_g` optional defaulting to `0`. The UI claimed all four macros were mandatory. `*` removed from Protein/Carbs/Fat; retained on Calories and Food name. No validation, defaults, zero behavior, cross-check warning, payload, or save path changed — harness section 27 pins the contract and that the indicators agree with it.

**4. Bare client `Loading...` fallbacks — replaced with the route skeletons.** `/nutrition`, `/food/saved`, and `/profile` are pre-existing client pages whose own `if (loading)` branch rendered bare centered text *after* the route-level `loading.tsx` resolved (the route file only covers server-suspense during navigation; the client fetch state is a second, independent loading surface). Each page now imports and returns its own route `loading.tsx` component — the navigation skeleton and the client fetch skeleton are byte-identical, with no duplication, no fake values, `aria-hidden` inherited, no spinner, no shred-card, no viewport trap. Query timing and client/server architecture unchanged. One prior check retargeted (flagged): "saved page keeps its pre-existing client loading text" pinned the retired bare text and now pins the skeleton reuse.

Correction scope: 7 feature/source files (select.tsx, AddFoodForm.tsx, nutrition/page.tsx, food/saved/page.tsx, profile/page.tsx, plus the authorized shared-shell files src/app/layout.tsx and src/app/(app)/layout.tsx; four are new to the 4B.6C file list — globals.css was touched during the failed height experiment and restored byte-identical), under the 10-file stop rule. Harness: 220 → 270 checks.
